# 01 · 接入 ft8_w 新解码库计划（路线 C · 双库并存）

> 本文件为实现计划（Plan），用于把 `D:\Desktop\ft8_w` 的新解码库接入
> `D:\Desktop\FT8CN_wty`（FT8CN）。执行过程中每完成一步都会 `git commit`。

---

## 1. 背景

FT8CN 原有解码实现在预编译库 `libft8cn.so` 内，源码不在本仓库。上游
`ft8_lib`（MIT，Kārlis Goba）的改造版 `ft8_w` 已完成以下能力并通过测试：

| 能力 | ft8_w 实现 | 状态 |
| --- | --- | --- |
| 瀑布谱找候选 → LDPC(BP) | `src/monitor.c` / `src/decode.c` / `src/ldpc.c` | ✅ P0 |
| 多线程候选解码 | `api/ft8api.c`（按候选区间切分，上限 `ft8_cpu_count()`） | ✅ P0 |
| 多遍重合成相减（SIC） | `api/ft8_subtract.c` + `enable_subtract` / `decode_depth` | ✅ P1 |
| OSD 兜底译码 | `api/ft8_osd.c` + `osd_depth`（默认 2） | ✅ P2.1 |
| 逐符号频谱 SNR（WSJT-X 同源噪声底） | `api/ft8_spectrum.c` | ✅ P2.2 |
| 按频率分段并行（可选） | `ft8_decode_config_t.num_bands` | ✅ P3（JNI 未暴露） |

性能参考（x86_64 模拟器、4 线程）：单遍 ≈12.5 ms；`--subtract --depth 3`
P95 ≈ 372 ms；叠加 OSD 后 P95 ≈ 234 ms。均远低于 FT8CN 的 15 秒单周期预算。

结论：**算法层面无需新建，只需把新库接入 FT8CN 的解码路径。**

---

## 2. 目标与非目标

### 目标
- FT8CN 的解码路径改用 `ft8_w` 新库，获得更高召回率与更准的 SNR。
- 其余功能（发射、频谱显示、呼号哈希、重采样、日志、电台控制）**保持不变**。
- 双库并存、互不干扰，可回滚。

### 非目标
- 不改 FT8CN 的发射/电台控制/日志链路。
- 不做 FT4（FT8CN 现 `FT4_MODE` 为预留，实际解码路径硬编码 FT8）。
- 不引入 32 位 `x86` ABI。

## 3. 总体架构

```
FT8CN App
├─ libft8cn.so（原库，完全保留）
│     ├─ 发射：pack77 / packFreeTextTo77 / ft8_encode / synth_gfsk
│     ├─ 呼号哈希：getHash10 / getHash12 / getHash22
│     ├─ 频谱：getFFTData / getFFTDataFloat / getFFTDataRaw / getFFTDataRawFloat
│     └─ 重采样：FT8Resample.*
└─ libft8.so（ft8_w 新库，新增）
      └─ 解码：瀑布 → 候选 → LDPC(BP) → OSD 兜底 → 多遍 SIC → 文本 + 噪声底 SNR
```

**符号隔离（关键）**：新库 JNI 符号为 `Java_com_ft8_nativecore_Ft8Native_*`，
老库为 `Java_com_bg7yoz_ft8cn_*`，包名不同，不会撞符号。因此老库一行不用改。

## 4. 关键设计决策

| # | 决策 | 原因 |
| --- | --- | --- |
| 1 | 新库沿用 `libft8.so` + `loadLibrary("ft8")`，不改名 | 双库并存靠包名隔离已足够，改名无收益 |
| 2 | 新库放 `ft8cn/app/libs/{arm64-v8a,armeabi-v7a,x86_64}/libft8.so` | 沿用现有 `sourceSets.jniLibs.srcDirs=['libs']` |
| 3 | 删除 `app/libs/x86/libft8cn.so`，`build.gradle` 加 `abiFilters` 锁定 3 ABI | 防止两库 ABI 不一致导致的 `UnsatisfiedLinkError` |
| 4 | 在 ft8_w 分支扩展 JNI，直接返回结构化字段 | `Ft8Message` 需要 `i3/n3/call_from/call_to/extra`，C 内部 `ftx_message_t` 已有，直接传出比在 Java 反解析可靠 |
| 5 | FT8CN 不再走 `ReBuildSignal` / `A91List` | SIC 已在新库内部，两套不能叠加；类文件保留但不再调用 |
| 6 | `deepDecodeMode` 映射为解码配置 | 复用现有设置项：深度 → `enable_subtract=true, decode_depth=3, osd_depth=2`；普通 → `enable_subtract=false, osd_depth=2` |
| 7 | `num_threads = min(CPU 核数, 4)` | 按设备核数匹配，同时控住功耗 |
| 8 | 新库 `snr`（float）第一版截断为 int 填入 `Ft8Message.snr` | 保持 UI/日志/ADIF 兼容，避免连带改动 |

## 5. 接口契约

### 5.1 结果串格式

现状（ft8_w `native/jni/ft8_jni.cpp`）：

```
text|snr|dt|freq|score|ldpc_errors|pass|ap_type|crc
```

S2 扩展后（追加字段，保持前缀兼容）：

```
text|snr|dt|freq|score|ldpc_errors|pass|ap_type|crc|i3|n3|call_from|call_to|extra|grid
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `text` | string | 解码文本 |
| `snr` | float | 上报信噪比 (dB) |
| `dt` | float | 相对时隙起点时间偏移 (s) |
| `freq` | float | 音频频率 (Hz) |
| `score` | int | Costas 同步分 |
| `ldpc_errors` | int | LDPC 残余错误数 |
| `pass` | int | 第几遍解出（0 基） |
| `ap_type` | int | AP 类型（当前恒 0） |
| `crc` | uint | CRC-14 |
| `i3`/`n3` | int | 消息类型字段 |
| `call_from`/`call_to` | string | 收/发呼号 |
| `extra` | string | 扩展信息（报告/73/网格等） |
| `grid` | string | 网格（可空） |

### 5.2 解码配置 float[] 下标（沿用 ft8_jni.cpp `DC_*`）

`0 fMinHz, 1 fMaxHz, 2 sampleRate, 3 timeOsr, 4 freqOsr, 5 maxCandidates,
6 minSyncScore, 7 ldpcIterations, 8 decodeDepth, 9 apMode, 10 enableSubtract,
11 numThreads, 12 returnDuplicates, 13 osdDepth, 14 enableLlrRefine`

## 7. 风险与对策

1. **结构化字段兼容**：`Ft8Message` 的 `i3/n3`、非标准呼号 `<...>` 的哈希解析
   现在由老 native 直接写 Java 对象。→ S2 必须传全等价字段；S9 重点验证
   "哈希呼号""自由文本"两类。
2. **SNR 口径变化**：新库 SNR 为 float 且重新标定，数值会变。→ 第一版截断为
   int，先保证不崩不错位，数值评估单独做。
3. **耗时**：SIC+OSD 后 P95 ≈ 234–372 ms（x86_64、4 线程），低端 ARM 真机可能更慢。
   → 保留超时保护，S9 记录耗时。
4. **`afterDecode` 的 `isDeep` 语义**：老逻辑用"深度解码的弱信号"标记
   `msg.isWeakSignal`。→ 按新库 `pass` 字段（第几遍解出）重新映射。
5. **`num_bands` 未暴露到 JNI**：第一版不用；如后续需要频率分段并行，再加下标。

## 9. 环境与构建命令

- ft8_w 主机构建/回归：
  ```bash
  cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
  cmake --build native/build --config Release
  ft8_cli bench test --threads 4 --subtract --depth 3 --osd 2
  ```
- ft8_w Android 交叉编译（NDK 28.2.13676358 / CMake 3.22.1 / Ninja）：
  ```bash
  NDK=$ANDROID_SDK/ndk/28.2.13676358
  for ABI in arm64-v8a armeabi-v7a x86_64; do
    cmake -S native -B native/build-android-$ABI -G Ninja \
      -DCMAKE_TOOLCHAIN_FILE=$NDK/build/cmake/android.toolchain.cmake \
      -DANDROID_ABI=$ABI -DANDROID_PLATFORM=android-24 -DCMAKE_BUILD_TYPE=Release
    ninja -C native/build-android-$ABI ft8
  done
  ```
- FT8CN 构建：`cd ft8cn && gradlew.bat assembleDebug`
