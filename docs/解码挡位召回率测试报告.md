# 解码挡位召回率测试报告

- 测试日期：2026-10-22
- 测试对象：FT8CN 六个解码挡位（快速解码、多次解码、wsjtx普通、wsjtx深度、wsjtx普通多核、wsjtx深度多核）
- 测试集：`D:\Desktop\ft8_w\test`
- 测试设备：
  - 模拟器：`sdk_gphone16k_x86_64`，API 37，4 核 x86_64
  - 真机：华为 `LRA-AL00`（Kirin 710，8 核，Android 10 / API 29，arm64-v8a）
- 被测 APK：`assembleDebug`，原生库为 `libft8cn.so` 与 `libwsjtx_Android.so`（mfsk-core / mfsk-ffi 0.12.0）

## 1. 测试方法

测试集共 **60 组 wav/txt**，参考报文合计 **1298 条**。每组音频都是 12 kHz、单声道、16 bit、15 秒整时隙。

每个挡位都调用 App 正式的挡位解码路径（debug 包中的 `BenchmarkActivity`），然后按 `ft8_w` 的 `ft8_cli` 相同口径比对：

1. 取报文的前 3 个空格分隔 token；
2. 统一转大写；
3. 任意 `<...>` 形式的哈希呼号归一化为 `<...>`；
4. 期望行保留重复（与 `ft8_cli` 一致）。

召回率 = 命中数 / 期望消息数；多余（extra）= 解出但不在参考中的报文数。

### 2.4 旧设备最终配置（4 段 + 2 轮 SIC + session 复用 + LTO）

这是按“85% 召回 / 平均 <700 ms”目标落地的最终配置：

- 频段数：`min(CPU 核心数, 4)`，8 核设备也只用 4 段；
- SIC：2 轮；
- 每段复用独立 session，不再每时隙 open/close；
- fat LTO + codegen-units=1 + panic=abort，JNI 层 `-O3`。

| 挡位 | 命中/期望 | 召回率 | 多余 | 平均 | P50 | P95 | 最大 |
|---|---:|---:|---:|---:|---:|---:|---:|
| wsjtx普通多核（第 1 次） | 1145/1298 | **88.2%** | **94（7.2%）** | **684.9 ms** | 636 ms | 904 ms | 1009 ms |
| wsjtx普通多核（第 2 次） | 1145/1298 | **88.2%** | **94（7.2%）** | **687.4 ms** | 637 ms | 907 ms | 1014 ms |
| wsjtx深度多核 | 1145/1298 | **88.2%** | **94（7.2%）** | **690.4 ms** | 641 ms | 924 ms | 1016 ms |

结论：

- 召回率 **88.2%**，高于 85% 目标；
- 平均耗时 **685~690 ms**，低于 700 ms 目标；
- 多余 **94 条（7.2%）**，与 4 段 session 复用前完全一致，没有因为优化而增加；
- 两次连续运行命中数、多余数完全相同，结果稳定；
- P95 仍在 900 ms 左右，目标只覆盖“平均值”。

**重复性验证（第二次完整重跑）**：命中仍为 1145/1298，多余仍为 94，平均 **681.6 ms**（P50 626 ms，P95 903 ms）；JTDX 两次运行逐文件解码集合也完全一致。

**跨设备验证（vivo V2338A，骁龙 8 Gen 3）**：同一配置下命中仍为 **1145/1298（88.2%）**、多余仍为 **94**，平均 **230.4 ms**，P50 219 ms，P95 319 ms，最大 348 ms。说明解码结果与设备无关，设备只影响耗时。

“多余”是相对参考 txt 而言，不等于伪码。本轮**没有启用 Min-Sum/OMS**，因此不存在近似译码额外引入的伪码；如需区分真信号与伪码，需要用 JTDX 对同一批 WAV 做逐条交叉验证（见 2.5）。

### 2.5 JTDX 交叉验证（94 条 extra）

验证工具：**JTDX Contest Edition 3.0.0-rc10** 的独立解码器 `jtdxjt9.exe`，参数：

```text
jtdxjt9 -8 -d 3 <wav>
```

不使用 mycall/grid/AP hint，同一批 60 个 WAV。

| 指标 | 数量 |
|---|---:|
| 我们的 extra | 94（7.2%） |
| **JTDX 也解出（确认）** | **67（71.3%）** |
| JTDX 未解出（未确认） | 27（占 1298 条的 2.08%） |
| JTDX 对参考 txt 的召回 | 1278/1298（98.5%） |
| JTDX 的 extra | 176（13.6%） |

进一步分析 27 条未确认报文：

- **25/27** 的呼号在 JTDX 其它文件的解码结果里出现过，说明是真实存在的电台；
- 未确认报文的 SNR 中位数约 **-9 dB**，最低 -22 dB，看起来是弱信号而非明显乱码；
- 因此 27 条更可能是“JTDX 这一轮也漏掉的弱信号”，而不是伪码。

保守估计：即使把 27 条全部当成伪码，伪码率上限是 **2.08%**；已有 67 条被 JTDX 独立确认，实际伪码率应更低。

注意：JTDX Contest Edition 是比 mfsk-core 更激进/更新的解码器（98.5% 召回、176 条 extra），这里只用它做“extra 是否真实存在”的独立佐证，不用于横向比较召回率。

**重复性**：第二次完整重跑后，我们的命中/extra/确认/未确认仍为 **1145 / 94 / 67 / 27**，JTDX 两次输出的逐文件解码集合完全一致。

逐条明细：

- `jtdx_crosscheck.tsv`：每个文件的 expected / ours / JTDX / confirmed / unconfirmed；
- `decoded_wsjtx_parallel.tsv`：我们最终配置解出的每一条报文（含 SNR/dt/freq）；
- `jtdx_decoded_all.txt`：JTDX 对 60 个 WAV 的原始解码输出。

## 3. 结论

1. **wsjtx 挡位明显领先**：85.7% 对比快速解码 72.4%，召回率提升 **13.3 个百分点**，漏解从 358 条降到 185 条。
2. **逐文件对比**：wsjtx 在 44/60 个文件中优于快速解码，4 个文件持平，12 个文件略低（差 1~5 条）。整体优势主要来自高密度时隙。
3. **多次解码收益有限**：只比快速解码多 6 条（+0.5 个百分点），但耗时约为 5 倍。当前测试集上 FT8CN 原有多次解码的减法收益不明显。
4. **wsjtx普通与 wsjtx深度（单实例）结果完全相同**：mfsk-ffi 的默认参数已经是 `BP_ALL_OSD + NORMAL`，当前“深度”只把 strictness 改为 `DEEP`，在本测试集上没有额外命中。多核档在旧设备上普通/深度也都是 88.2%。若希望深度档真正更强，需要进一步启用 SIC 轮数、AP hint 或更大候选数。
5. **多余率与伪码**：最终配置为 94 条（7.2%）。JTDX Contest Edition 对同一批 WAV 交叉验证后，**67 条被 JTDX 独立解出**（71.3%），27 条未确认；其中 25 条的呼号在 JTDX 其它文件中出现过。即使把 27 条全部算作伪码，伪码率上限也只有 **2.08%**。
6. **旧设备最终配置达到目标**：4 段 + 2 轮 SIC + session 复用 + LTO，在 Kirin 710 上召回 **88.2%**、平均 **685 ms**、多余 94 条，满足“≥85% 召回、平均 <700 ms”。
7. **段数不是越多越好**：旧设备上 8 段会同时做 8 次整时隙 FFT，内存带宽/缓存争用反而更慢（2 轮 SIC 下 8 段约 816 ms，4 段约 685 ms）。因此自动分段上限固定为 4。

## 4. 测试中发现并修复的问题

### 4.1 wsjtx 报文还原把网格误判为呼号

初版 wsjtx 挡位召回率只有 56.9%，排查发现是**报文还原逻辑的 bug**：

- mfsk-core 原始报文：`CQ OK6LZ JN99`
- 错误还原为：`CQ JN99`（把网格 `JN99` 当成了呼号，`OK6LZ` 被当成 CQ 修饰符）

修正方式：只有第三个 token 不是梅登海德网格时，才把第二个 token 当作 CQ 修饰符。

修复后：

- 召回率：56.9% → 85.7%；
- 文本一致性校验：60/60 个文件，mfsk 原始报文与 `Ft8Message.getMessageText()` 还原结果 **0 处差异**。

### 4.2 真机“首次解码 7 秒、第二次 100 ms”

**现象**：真机正常监听时，第一次解码耗时约 7 秒，下一次只有约 100 ms。

**根因 1（7 秒）**：wsjtx 解码成功后的 `afterDecode` 回调里，`DatabaseOpr.addCallsignQTH()`
对 `null` 网格调用 `trim()` 抛出 NPE。这个 NPE 被 `decodeByWsjtxParallel()` 的
`catch (Throwable)` 当成“解码失败”，于是依次又执行了：

1. 单实例 wsjtx 解码（约 4.5 秒）；
2. 再次回调，再次 NPE；
3. 回退原 FT8CN 解码器。

三段耗时叠加后正好约 7.7 秒。

**根因 2（100 ms）**：没有消息的安静时隙本身只需要约 100 ms；而每个进程的第一次解码
还要加载原生库、创建 8 线程池、触发 FFT planner 初始化，约 0.9~1.0 秒。

**修复**：

1. wsjtx 消息的 `maidenGrid` 默认置为空字符串，不再为 `null`；
2. `DatabaseOpr.addCallsignQTH()` 增加 `grid == null` 保护；
3. **回调异常不再影响解码流程**：
   - wsjtx 解码与结果发布分离；
   - `afterDecode` 统一由 `safeAfterDecode()` 调用，异常只记录日志，绝不触发重新解码或回退；
   - 原 FT8CN 解码路径的回调也改用 `safeAfterDecode()`，避免下游异常杀死解码线程。

**真机复测**（连续 4 个时隙）：

| 时隙 | 解码条数 | 耗时 | 说明 |
|---|---:|---:|---|
| 1 | 0 | 981 ms | 进程冷启动（加载库、建线程池） |
| 2 | 22 | 3018 ms | 正常并行解码 |
| 3 | 13 | 2841 ms | 正常并行解码 |
| 4 | 20 | 3124 ms | 正常并行解码 |

不再出现 7 秒回退，也没有 NPE。

## 7. 多核挡位实现说明

- mfsk-ffi 的 `MfskDecodeParams` 本身支持 `freq_min_hz` / `freq_max_hz`，因此不需要带通滤波或移频；每段直接只搜索自己的频段，频率、dt、SNR 保持原值。
- JNI 新增 `nativeDecodeBand(..., freqMin, freqMax)` 和带速度档位的 `nativeDecodeBandEx`；`WsjtxDecoder` 增加对应的 Java 重载。
- `WsjtxBandDecoder` 负责分段：
  - 范围 100~3000 Hz，段间重叠 100 Hz（左右各 50 Hz）；
  - 段数 = `min(CPU 核心数, 4)`，每段至少 200 Hz 核心宽度；
  - 固定大小线程池，每个频段复用独立的 mfsk session，不再每时隙 open/close；
  - 生产默认速度档位为 2 轮 SIC（`profile = 6`）；
  - 结果按报文文本去重（保留 SNR 较高的一条），再按频率排序。
- 失败回退顺序：多核分段失败 → 单实例 wsjtx → 原 FT8CN 解码器。
- Android 普通应用无法绑定指定 CPU 核心，这里是线程池 + 系统调度。
- 编译优化：Rust 使用 fat LTO、`codegen-units=1`、`panic=abort`，JNI C 层使用 `-O3`。

## 8. 说明

- 解码耗时是单次调用墙钟时间；4 段配置下每段 session 复用，耗时中不再包含每时隙 open/close。
- 最终配置在旧设备上平均 685~690 ms、P95 约 900 ms；700 ms 目标只覆盖平均值，P95 仍会超过。
- 真机持续跑完多个挡位后电池温度从 28°C 升到 37°C；多核挡位会更充分地使用 CPU，长时间监听时需注意发热和续航。
- 模拟器与真机的召回率有极小差异，属于 x86_64/arm64 浮点与 OSD 边界差异。
- 多次解码的 7 秒超时在本轮未触发（模拟器最大 197 ms，旧设备最大 1243 ms）。
