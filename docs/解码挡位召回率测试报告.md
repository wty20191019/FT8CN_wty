# 解码挡位召回率测试报告

- 测试日期：2026-10-22
- 测试对象：FT8CN 四个解码挡位（快速解码、多次解码、wsjtx普通、wsjtx深度）
- 测试集：`D:\Desktop\ft8_w\test`
- 设备：Android x86_64 模拟器（`sdk_gphone16k_x86_64`，API 37）
- 被测 APK：`assembleDebug`，原生库为 `libft8cn.so` 与 `libwsjtx_Android.so`（mfsk-core / mfsk-ffi 0.12.0）

## 1. 测试方法

测试集共 **60 组 wav/txt**，参考报文合计 **1298 条**。每组音频都是 12 kHz、单声道、16 bit、15 秒整时隙。

每个挡位都调用 App 正式的挡位解码路径（debug 包中的 `BenchmarkActivity`），然后按 `ft8_w` 的 `ft8_cli` 相同口径比对：

1. 取报文的前 3 个空格分隔 token；
2. 统一转大写；
3. 任意 `<...>` 形式的哈希呼号归一化为 `<...>`；
4. 期望行保留重复（与 `ft8_cli` 一致）。

召回率 = 命中数 / 期望消息数；多余（extra）= 解出但不在参考中的报文数。

## 2. 测试结果

| 挡位 | 命中/期望 | 召回率 | 漏解 | 多余 | 平均耗时 | P50 | P95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 快速解码 | 940/1298 | **72.4%** | 358（27.6%） | 50（3.9%） | 28.9 ms | 23 ms | 58 ms |
| 多次解码 | 946/1298 | **72.9%** | 352（27.1%） | 53（4.1%） | 142.4 ms | 140 ms | 159 ms |
| wsjtx普通 | 1113/1298 | **85.7%** | 185（14.3%） | 87（6.7%） | 439.8 ms | 431 ms | 580 ms |
| wsjtx深度 | 1113/1298 | **85.7%** | 185（14.3%） | 87（6.7%） | 435.0 ms | 428 ms | 588 ms |

参考对照（`D:\Desktop\ft8_w\native\build-clang\ft8_cli.exe bench`，宿主 PC 4 线程，属于另一套解码器，仅供横向参考）：

| 解码器 | 命中/期望 | 召回率 | 多余 | 平均耗时 |
|---|---:|---:|---:|---:|
| ft8_w 默认配置 | 956/1298 | 73.7% | 28（2.2%） | 54.9 ms |

## 3. 结论

1. **wsjtx 挡位明显领先**：85.7% 对比快速解码 72.4%，召回率提升 **13.3 个百分点**，漏解从 358 条降到 185 条。
2. **逐文件对比**：wsjtx 在 44/60 个文件中优于快速解码，4 个文件持平，12 个文件略低（差 1~5 条）。整体优势主要来自高密度时隙。
3. **多次解码收益有限**：只比快速解码多 6 条（+0.5 个百分点），但耗时约为 5 倍。当前测试集上 FT8CN 原有多次解码的减法收益不明显。
4. **wsjtx普通与 wsjtx深度结果完全相同**：mfsk-ffi 的默认参数已经是 `BP_ALL_OSD + NORMAL`，当前“深度”只把 strictness 改为 `DEEP`，在本测试集上没有额外命中。若希望深度档真正更强，需要进一步启用 SIC 轮数、AP hint 或更大候选数。
5. **多余率**：wsjtx 为 87 条（6.7%），其中包含参考 txt 未记录的报文（例如 `<...> E77VM R-11`、`CQ R7NO KN98`、`OE3MLC G3ZQQ 73`），不一定是误码，后续可用多解码器交叉验证。

## 4. 测试中发现并修复的问题

初版 wsjtx 挡位召回率只有 56.9%，排查发现是**报文还原逻辑的 bug**：

- mfsk-core 原始报文：`CQ OK6LZ JN99`
- 错误还原为：`CQ JN99`（把网格 `JN99` 当成了呼号，`OK6LZ` 被当成 CQ 修饰符）

修正方式：只有第三个 token 不是梅登海德网格时，才把第二个 token 当作 CQ 修饰符。

修复后：

- 召回率：56.9% → 85.7%；
- 文本一致性校验：60/60 个文件，mfsk 原始报文与 `Ft8Message.getMessageText()` 还原结果 **0 处差异**。

## 5. 复现方式

```powershell
# 1. 构建并安装 debug 包（BenchmarkActivity 只在 debug 源集）
cd D:\Desktop\FT8CN_wty\ft8cn
.\gradlew.bat assembleDebug

# 2. 推送测试集
adb push D:\Desktop\ft8_w\test\. `
  /sdcard/Android/data/com.bg7yoz.ft8cn/files/ft8test/

# 3. 运行指定挡位（fast / deep / wsjtx / wsjtx_deep）
adb shell am force-stop com.bg7yoz.ft8cn
adb shell am start -n com.bg7yoz.ft8cn/.ft8listener.BenchmarkActivity `
  --es dir /sdcard/Android/data/com.bg7yoz.ft8cn/files/ft8test `
  --es modes fast

# 4. 查看结果
adb logcat -s FT8Bench:I
adb pull /sdcard/Android/data/com.bg7yoz.ft8cn/files/bench_fast.txt
```

可选参数：`--es file test_01.wav` 只跑单个文件；`--ez dump true` 输出逐条 EXP/GOT/MISS；`--ez checktext true` 校验文本还原一致性。

## 7. 说明

- 解码耗时是模拟器单次调用墙钟时间，真机耗时会不同；召回率只受算法影响，真机应一致。
- 多次解码的 7 秒超时在本轮未触发（最大 197 ms）。
- wsjtx 每次调用 `decodeOnce` 会重新 open/close session，耗时中包含这部分开销。
