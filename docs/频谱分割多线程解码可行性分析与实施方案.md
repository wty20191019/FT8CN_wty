## 1. 结论摘要

1. **现有两种深度**是布尔开关：`GeneralVariables.deepDecodeMode`。快速模式 LDPC 迭代 20 次；深度模式迭代 200 次，并在 7 秒预算内反复“解码 → 抵消已解信号 → 再解码”。
2. **底层解码器是预编译动态库** `libft8cn.so`，仓库里没有 C 源码，`build.gradle` 中的 `externalNativeBuild` 已被注释，当前只打包 `app/libs/<abi>/libft8cn.so`。这是本次改造最大的约束。
3. 但底层解码器是**按实例分配状态**的（候选表、瀑布图、哈希表、A91 缓冲都在 `decoder_t` 内），因此“一个线程一个解码器实例”在结构上成立。
4. **JTDX 的并行不是音频带通，而是“候选搜索范围”切分**：JTDX 每段仍使用完整 12 kHz 音频和全带宽频谱，只在本段频率范围内提取候选。这样没有滤波器边界损失，也不需要重叠频段。
5. 不修改现有 native 库有三种可行路线：
   - **路线 A0（JTDX 等价，推荐先验证）**：写一个很小的 JNI shim，调用现有库已导出的 `setMagToZero()`，在瀑布图上屏蔽本片之外的频点。没有音频滤波损失；每片仍做全带宽 FFT/同步。
   - **路线 A（回退）**：把 12 kHz 音频按频段做带通滤波，每个频段一个解码器实例并行解码。实现简单，但有滤波开销和边界衰减，需要保护带/重叠。
   - **路线 B（高性能）**：每个频段先移频、再低通抽取到较低采样率，再交给解码器。由于解码器的 FFT 点数、频率格点数都随采样率线性缩放，单段计算量按带宽下降，理论上可接近线性加速。
6. **直接改 0.93（路线 C）不可行**：0.93 的 C 源码未公开，仓库历史里只能恢复 0.89 版源码；0.93 新增的深解码、浮点输入、A91、信号抵消等改动缺失。
7. **原版 ft8_lib 提供了更优的路线 D**：本机 `D:\Desktop\ft8_lib` 是 kgoba/ft8_lib 完整源码，其 `monitor` 的 `f_min/f_max` 真实生效，支持任意采样率，实例状态干净。可以基于它新建一个解码核心，实现“**一次 FFT 生成共享瀑布图 + 固定切片 + 每片独立候选搜索 + 并行 LDPC 解码**”，没有滤波损失、没有重复 FFT、没有版本绑定 shim。
8. **推荐实施顺序**：
   - 想尽快验证效果：先做路线 A0（shim 屏蔽），1 周内可拿到真机数据；
   - 想做长期正确、速度和召回都最优的版本：选路线 D，先做桌面 PoC，再包 JNI；约 3～5 周，主要成本在消息字段映射和深解抵消移植。
9. 深度模式的时间上限固定为 7 秒。并行化即使不降低总耗时，也能在同样 7 秒内完成更多轮“抵消 + 重解”，**弱信号解码数量有望增加**，这是比“更快”更有价值的收益。

### 1.1 兼容性硬约束（用户要求）

**快速解码和深度解码必须保留原有实现，不能被替换、改写或改变行为。** 具体约束：

1. **旧解码链路完全保留**：
   - `FT8SignalListener.decodeFt8()`、`runDecode()`、`ReBuildSignal.subtractSignal()` 等旧路径不删除、不改写；
   - 现有 `libft8cn.so` 不重新编译、不替换、不改 JNI 签名；
   - 旧快速模式的 20 次 LDPC 迭代、旧深度模式的 200 次迭代 + 7 秒抵消循环，参数和行为保持不变。

2. **新模式只在被选中时生效**：
   - 默认仍是快速解码；
   - 只有用户选择“并行解码”时，才进入新核心；
   - 切换回快速/深度时，必须回到原来的代码路径，结果和耗时与修改前一致。

3. **配置向后兼容**：
   - 保留现有 `deepMode` 键及其 `0/1` 语义；
   - 新增 `decodeMode` 键只用于区分“快速 / 深度 / 并行”三态；
   - 旧版本配置（只有 `deepMode`）升级后，快速/深度行为不变。

4. **故障隔离**：
   - 新核心初始化失败、ABI 不匹配、线程异常时，自动降级到旧深度模式；
   - 新核心不得影响旧模式的 decoder 生命周期、内存和线程。

5. **回归验收**：
   - 同一段 WAV 下，快速/深度模式的消息集合、顺序、时间偏移、SNR、解码耗时与修改前一致（允许测量误差）；
   - 关闭并行模式后，`libft8cn.so` 的调用次数和参数与修改前一致。

> 因此，推荐采用“**独立新核心 + 入口分发**”的方式：旧模式路径原样保留，只在 `decodeFt8()` 入口增加一个“是否并行模式”的分支；并行分支使用新的 `libft8parallel.so`，不碰旧 native 库。

### 2.2 解码调用链

核心在 `ft8cn/app/src/main/java/com/bg7yoz/ft8cn/ft8listener/FT8SignalListener.java`：

1. `UtcTimer` 每 15 秒触发一次 `runRecorde()`（`:57-67`、`:97-110`）。
2. 录音完成后回调 `decodeFt8(utc, voiceData)`（`:112`）。
3. `decodeFt8()` 内部 `new Thread(...)` 启动**一个**后台线程（`:121-185`）。
4. 线程内：
   - `InitDecoder(utc, 12000, voiceData.length, true)` 创建解码器（`:134`）；
   - `DecoderMonitorPressFloat(voiceData, ft8Decoder)` 生成瀑布图（`:137`）；
   - 第一轮 `runDecode(..., false)` 快速解码（`:143`）；
   - 若 `deepDecodeMode` 为真，再跑一轮 `runDecode(..., true)`，然后进入“抵消信号 + 再解码”循环（`:152-178`）。
5. `runDecode()`（`:189-228`）：
   - `setDecodeMode(decoder, isDeep)`（`:197`）：`isDeep=true` 时把 LDPC 迭代次数设为 200，否则 20；
   - `DecoderFt8FindSync(decoder)`（`:199`）：最多返回 120 个候选；
   - 遍历候选调用 `DecoderFt8Analysis(idx, decoder, ft8Message)`（`:204`）；
   - 成功后取 `DecoderGetA91(decoder)` 存入 `A91List`（`:208-209`）；
   - 消息去重（`checkMessageSame`，按消息文本，`:269-279`）。
6. 信号抵消：`ReBuildSignal.subtractSignal(ft8Decoder, a91List)`（`ft8listener/ReBuildSignal.java:19-26`），逐个信号调用 native 的 `doSubtractSignal`。

### 2.3 底层解码器的结构（基于可恢复的 0.89 源码）

仓库在提交 `9ad039f`（“cpp del”）中删除了全部 C/C++ 源码；其父提交 `65c3857`（“Ver. 0.89”）仍可完整恢复：

```
ft8CN/app/src/main/cpp/
├── CMakeLists.txt
├── ft8Decoder.c / .h
├── ft8Listener.cpp
├── monitor_opr.c / .h
├── ft8/decode.c、ldpc.c、constants.c ...
└── fft/kiss_fft.c、kiss_fftr.c
```

从 0.89 源码可以确认以下事实：

- `init_decoder()` 动态分配 `decoder_t`，每个实例独享：
  - `candidate_list[120]`
  - `decoded[100]` 与 `decoded_hashtable[100]`
  - `a91[]`
  - `monitor_t mon`（瀑布图 `mag`、`mag2`、窗函数、FFT 工作区）
  - `kLDPC_iterations`
- `monitor_config_t` 里有 `f_min = 100`、`f_max = 3000`，但在 0.89 的 `ft8_find_sync()` 中**没有被使用**：同步搜索仍从 `freq_offset = 0` 一直扫到 `num_bins - 7`。
- 瀑布图参数全部由采样率推导：
  - `block_size = sample_rate * 0.16`
  - `nfft = block_size * 2`
  - `num_bins = sample_rate * 0.16 / 2`
  - 频率格点间距恒为 6.25 Hz（与采样率无关）
- 一次 15 秒、12 kHz 的瀑布图：93 个符号 × 2 个时间子采样 = 186 次 3840 点 FFT，`mag` 约 357 KB，`mag2` 约 1.4 MB。
- 同步搜索规模：`2 × 2 × 36 × (960 - 7) ≈ 27.4 万` 次评分，每次评分累加 21 个 Costas 符号。
- 深度模式的 LDPC 迭代次数：`fast_kLDPC_iterations = 20`，`deep_kLDPC_iterations = 200`。
- 候选上限 `kMax_candidates = 120`，单实例已解消息上限 `kMax_decoded_messages = 100`。
- `decoder_ft8_reset()` 只重置瀑布图块数、最大幅度、UTC 和样本数，**不清理已解消息哈希表**。因此跨周期复用解码器会错误去重，当前实现是每周期新建、用完删除，这是正确的。

### 2.4 预编译库的实际情况

- 仓库中的 native 库：`ft8cn/app/libs/{arm64-v8a,armeabi-v7a,x86,x86_64}/libft8cn.so`。
- `ft8cn/app/build.gradle:32-37` 仍有 `externalNativeBuild` 的 `cppFlags` 配置，但真正的构建路径在 `:57-62` **被注释**；`:64-68` 只把 `libs` 当 `jniLibs` 打包。
- 当前机器没有安装 NDK/CMake（`local.properties` 指向的 SDK 下无 `ndk`、`cmake` 目录）。
- `.so` 内的调试路径显示其构建自 `G:/ft8CN_0.93_20250104/ft8CN/app/src/main/cpp/...`，即 **0.93 源码**。
- 上游 GitHub `N0BOY/FT8CN` 与 Gitee `bg7yoz/ft8cn` 的 0.93 仓库同样只提供 `.so`，没有 `cpp` 目录。
- `.so` 的动态符号表里可以看到 `init_decoder`、`decoder_monitor_press`、`decoder_ft8_find_sync`、`decoder_ft8_analysis`、`setMagToZero(decoder_t*, int, int)` 等符号。理论上可以写一个“小型 JNI shim”链接这些符号，但 `decoder_t`、`ft8_message` 的 0.93 内存布局未知，风险高，不建议作为主方案。

> 结论：**第一版不要在 native 层动刀**；把 native 当作黑盒，用“多实例 + 频谱分割”的方式并行。

### 2.5 当前线程与回调模型

- 每个 15 秒周期启动一个解码线程，没有取消机制；如果上一周期超过 15 秒未结束，会与下一周期重叠（目前靠 7 秒深度上限规避）。
- `onFt8Listen.afterDecode()` 在解码线程中直接回调（`FT8SignalListener.java:148、159、173`）。
- `MainViewModel.afterDecode()`（`MainViewModel.java:301-360`）会修改 `ft8Messages`、`currentMessages`、`currentDecodeCount` 等共享状态；虽然 `ft8Messages` 有 `synchronized`，但计数器和自动发射解析不是线程安全的。
- 自动发射只允许快速解码结果触发（`MainViewModel.java:318-325` 的 `!isDeep` 条件），深度结果被刻意屏蔽。
- 因此并行化后**不能从多个工作线程同时回调 `afterDecode()`**，必须由编排线程汇总后单线程回调。

## 3. 可行性分析

### 3.1 为什么按频谱分割可以加速

FT8 的候选搜索与解码是“频率局部”的：

- 一个 FT8 信号只占约 50 Hz；
- Costas 同步评分只访问该候选附近 8 个频点；
- LDPC/OSD 解码只使用该候选的 174 个软信息；
- 信号抵消也只影响该信号所在频点的瀑布图幅度。

因此，把 0～5950 Hz 切成若干片后，每片的候选数量约为原来的 `1/S`，**逐候选解码的耗时可以并行分摊**。

限制在于：现有 JNI 接口没有“只搜索某个频段”的参数，每个解码器仍会对整段音频做完整 FFT 并全频段找同步。因此：

- 若只做带通滤波（路线 A），固定开销（FFT + 同步）会重复 N 次；
- 若同时降采样（路线 B），固定开销也随带宽下降，才是真正的“按段分摊”。

### 3.2 五条实现路线对比

| 维度 | 路线 A0：瀑布图屏蔽（JTDX 等价） | 路线 A：同采样率带通分割 | 路线 B：移频 + 降采样分割 | 路线 C：改 0.93 native | 路线 D：原版 ft8_lib 共享瀑布 |
| --- | --- | --- | --- | --- | --- |
| 是否改现有 native | 新增小 shim，不改原库 | 否 | 否 | 是 | 否（新建独立核心） |
| 是否依赖 0.93 源码 | 否（依赖导出符号） | 否 | 否 | 是（当前拿不到） | **否** |
| 每段 FFT/同步开销 | 重复 S 次 | 重复 S 次 | 按带宽下降 | 只算一次 | **只算一次** |
| 逐候选解码 | 并行分摊 | 并行分摊 | 并行分摊 | 并行分摊 | 并行分摊 |
| 段边界损失 | 无（只屏蔽候选） | 有，需要保护带/重叠 | 有，需要保护带 | 无 | **无** |
| 预估加速比（深度轮次） | 1.3～2.2 倍 | 1.3～2.5 倍 | 2～4 倍（受核数限制） | 接近核数上限 | **接近核数上限** |
| 额外 DSP | 无 | 线性相位 FIR 带通 | 混频 + 低通 + 整数抽取 | 无 | 无 |
| 消息兼容性 | 与现版本完全一致 | 一致 | 一致 | 一致 | **需要映射/补齐** |
| 实现风险 | 中（符号/布局依赖） | 低 | 中 | 高（源码缺失） | 中高（消息/深解移植） |
| 适合作为第一版 | 快速验证 | 回退方案 | 第二阶段 | 不做 | **长期最优；有源码时首选** |

### 3.3 关键技术判断

#### （1）多解码器实例能否并行

从 0.89 源码看，解码状态全部在 `decoder_t` 内，没有发现可变的全局状态；`ft8/constants.c`、LDPC 生成矩阵等都是只读常量。`malloc`、`kiss_fft` 配置也都按实例分配。因此“一个线程一个 decoder”**结构上可行**。

但 0.93 是预编译库，不能 100% 保证线程安全。必须用 4 线程连续跑 1 小时做压力验证；如果出现崩溃或结果错乱，退回 2 线程或加全局锁（会损失并行度）。

#### （2）解码器是否支持非 12 kHz 采样率

`InitDecoder(utc, sampleRate, numSamples, isFt8)` 本身就接收采样率；0.89 源码中 `block_size`、`nfft`、`num_bins` 全部由它推导，且频率格点间距恒为 6.25 Hz。因此**结构上支持任意采样率**。

但 0.93 是否偷偷写死 12000，无法从二进制确认。路线 B 必须先做一个小实验：把一段 12 kHz 录音抽取到 4 kHz，确认 `InitDecoder(..., 4000, ...)` 仍能正确解码，再继续。

> 实测建议：用已知内容的 WAV（例如 `gen_ft8` 生成的信号）在 12000、6000、4000、3000、2000 Hz 下分别解码，比较文本、频率、时间偏移和 SNR。

#### （3）深度模式的“抵消 + 重解”如何跨段

- 每个频段解码器只处理本段音频，抵消时只抵消本段内的信号；段外信号本来就被滤除/抽取掉，不需要处理。
- 每轮结束后汇总所有频段的新消息，再进入下一轮；终止条件为“所有频段都没有新消息”或“达到时间上限”。
- 这样每段的哈希表上限（100 条）也独立，弱信号不容易被强信号挤掉，**解码数量可能比单实例更多**。

#### （4）结果合并与去重

- 现有 `checkMessageSame()` 只按消息文本去重；跨频段重复解码会被合并，并保留较高的 SNR。
- 频段重叠区可能同一信号被两个段解出，文本相同，天然去重。
- 建议保持现有语义，不改成“文本 + 频率”，避免影响既有行为和自动程序。

#### （5）不能通过 Java 层改变的 native 限制

- 候选上限固定 120/段；
- 单实例已解消息上限固定 100；
- LDPC 迭代次数只能 20 或 200；
- 同步阈值、时间偏移范围、Costas 评分算法均不可调。

因此“可设置参数”只能围绕**切片数、保护带、时间上限、是否降采样、线程数**做文章。

### 3.4 可行性判定

| 项目 | 判定 |
| --- | --- |
| 不改 native 实现频谱分割多线程 | **可行** |
| 不改 native 获得明显加速 | **可行，但受重复 FFT/同步限制** |
| 不改 native 获得接近线性加速 | **有条件可行**，取决于 0.93 是否支持任意采样率 |
| 改 native 做最优实现 | **当前不可行**，缺 0.93 C 源码 |
| 分段并行提高召回率 | **有条件**：只在候选数/消息表/时间存在上限时成立；理想无上限下不会 |
| 对现有快速/深度模式零影响 | **可控**，用独立模式分支 + 开关回退 |

### 3.5 频谱分割与召回率：在“参数无上限”假设下的边界分析

先定义召回率：

```
召回率 R = 正确解出的信号数 / 实际存在的信号数
```

结论取决于“参数无边”具体指什么：

| 假设 | 召回率是否提高 | 原因 |
| --- | --- | --- |
| 候选数、消息表、时间/迭代次数全部无上限，滤波器理想 | **不会** | 分割只是把同一个问题拆开，信息量不变；理论上等价于全带解码 |
| 仅时间/线程无上限，但保留每实例 120 候选、100 条已解消息 | **会，拥挤频段明显** | 每个频段独立获得一份候选/消息配额，总预算变成 N 倍 |
| 只并行、不分割（候选轮流分给线程） | **不会** | 候选集合和解码结果与单线程全带完全一致，只是变快 |
| 无上限，但滤波器非理想 | **可能略降** | 段边界信号被过渡带削弱，或群延迟/频率换算引入误差 |

#### （1）为什么“理想无上限”下不会提高

设全带解码器为 `D(x)`，理想带通滤波器为 `F_i`，第 i 段解码器为 `D_i`。如果：

- 滤波器是理想砖墙，频段之间无重叠损失；
- 每个候选的解码只使用本候选附近的频点（FT8 的 Costas 评分只访问 8 个频点，LLR 只取 174 个软信息）；
- 候选数、消息表、迭代次数、时间都不设上限；

那么：

```
D(x) = ∪ D_i(F_i · x)
```

分割前后能看到的信号、每个信号的 LLR、LDPC 解码结果都相同，**分割不会创造新信息**。并行只是把同样的工作分摊到多个线程，缩短墙钟时间，不改变召回率。

#### （2）当前实现下为什么会提高

现有 native 实现有三处“硬上限”，它们才是分段并行提高召回率的真正来源：

1. **每实例候选上限 `kMax_candidates = 120`**
   - 全带解码器只保留同步分最高的 120 个候选；
   - 强信号多、弱信号多的拥挤频段，弱信号会被挤出候选表；
   - 分成 S 片后，每片各有 120 个候选，总候选预算变成 `S × 120`，弱信号只要在本片排进前 120 就能被尝试。
   - 如果候选上限真的“无边”，这个收益就不存在。

2. **每实例已解消息上限 `kMax_decoded_messages = 100`**
   - 全带解码器一个周期最多保留 100 条唯一消息；
   - 分段后每段独立 100 条，总容量变成 `N × 100`；
   - 0.89 源码中哈希表满且找不到重复项时，探测循环可能无法退出，拥挤场景下这不仅是召回率问题，还是稳定性问题（0.93 是否修正未知）。

3. **7 秒深度预算**
   - 并行让每轮“同步 + 解码 + 抵消”更快，同样 7 秒内能跑更多轮；
   - 对重叠信号、弱信号而言，多一轮抵消就可能多解出一条；
   - 如果时间无上限，单实例最终也能跑完同样多的轮次，这个收益同样消失。

此外还有两个“非理想但实际存在”的因素：

- **带外强信号抑制**：带通/抽取后，强信号的窗泄漏、量化饱和、低频干扰对弱信号频点的影响会变小，弱信号的有效 SNR 可能略有改善；
- **抵消残差**：每段只抵消本段信号，参与抵消的信号更少，强信号抵消不准时对弱信号的污染更小。但抵消顺序会改变结果，不能保证单调提升。

#### （3）代价：召回率提高可能伴随精确率下降

- 候选总数从 120 变成 `N × 120`，误报（噪声被 CRC 误判为合法消息）概率也近似按 N 倍增加；
- FT8 使用 14 位 CRC，单候选误报概率很低，但在数百个候选、多轮深解、信号抵消的组合下不能忽略；
- 因此评估时必须同时统计**召回率**和**精确率**（解出的消息中真实消息的比例），不能只看“解出更多”。

#### （4）对本项目的结论

- 如果目标是“**同样 7 秒内尽量多解出弱信号**”，分段并行有效，但本质是“用 N 倍候选/消息预算 + 更多迭代轮次换召回率”，不是并行计算本身带来的信息增益。
- 如果目标是“**理论上限召回率**”，正确做法是提高单实例候选上限、消息表上限、改进信号抵消和 LDPC/OSD，而不是把频谱切碎；这些都需要 native 源码。
- 由于当前 native 候选上限固定且不可调，**切片数 S 事实上就是候选预算的倍数**。这一点应在 UI 帮助中明确提示，避免用户误以为“片数越多，算法越强”。
- 建议用两组基准验证收益来源：
  - **稀疏场景**（信号数 < 120）：分段并行应与深度模式基本持平；若明显更好，说明收益来自滤波/多轮迭代，而非候选上限；
  - **拥挤场景**（信号数 > 120）：分段并行应明显优于深度模式；这能直接证明收益来自“每段独立候选配额”。

### 3.6 JTDX 的并行实现及其启示

JTDX 确实采用“按频谱切分、每段一个线程”的并行方式，但实现细节和“音频带通分割”并不相同。查看 JTDX 源码可以确认：

1. **按线程数等分频段**
   `lib/decoder.f90:225-302`：2 线程时以 `nfmid` 为界，3 线程时用 `nfmid1/nfmid2`，4 线程时用 `nfmid1..nfmid3`，每个 OpenMP section 调用一次 `my_ft8%decode(..., nfa, nfmid, ...)`、`(..., nfmid+1, nfb, ...)` 等，频段首尾相接、互不重叠。

2. **每段只限制“候选搜索范围”，不做音频滤波**
   `lib/ft8_decode.f90:215` 把本段的 `nfa/nfb` 传给 `sync8`；
   `lib/sync8.f90` 中：
   - `ia = max(1, nint(nfa/df))`、`ib = max(1, nint(nfb/df))`，其中 `df = 3.125 Hz`；
   - 同步评分矩阵 `sync2d` 仍在**整个宽频带**（`iaw..ibw`）上计算；
   - 只在 `do i=ia,ib` 内提取候选。

   也就是说，JTDX 的每个线程仍然使用**完整的 12 kHz 音频和全带宽频谱**，只是不去查询本段之外的候选中心频率。因此：
   - 不需要音频带通滤波，不存在滤波器过渡带、群延迟和边界衰减；
   - 不需要靠“重叠频段”补救边界信号，因为信号的频谱本身是完整的；
   - 线程之间只共享只读的音频/频谱，切分的是候选集合。

3. **每个线程有独立的候选堆**
   `sync8.f90` 的局部数组是 `candidate0(5,450)`、`candidate(4,460)`，即每段最多 450 个候选（CE3TSK 的改造版提高到 2000）。这正是“分段提高召回率”的真正来源：每段独立配额，而不是并行计算本身。
   JTDX 还有多 pass、hint、信号抵消等机制，这些也都在提高召回率，不能全部归功于“并行”。

4. **线程数是否改变结果**
   - 上游 JTDX 直接按线程数切分，切换线程数会改变边界，结果可能有细微差异；
   - CE3TSK 的改造版把切片网格与线程数解耦：固定 417 Hz 网格、线程动态取片、按片序合并，并声称 1/3/6/12 线程结果一致；FT4 还使用“半切片偏移的第二遍”来覆盖边界信号。
   这从侧面证明：**并行本身不改变召回率，改变的是切片网格、候选上限和 pass 数量。**

5. **JTDX 与 FT8CN 的关键差距**
   - JTDX 的 `sync8` 支持 `nfa/nfb` 参数，所以可以“只限制候选范围”；
   - FT8CN 的 native `ft8_find_sync()` **没有频率范围参数**，固定扫描全部 bin；
   - JTDX 每段候选上限 450（改造版 2000），FT8CN 固定 120；
   - JTDX 默认覆盖 0～5000 Hz，FT8CN 的 native 实际扫描 0～约 5950 Hz（`num_bins = 960`，每 bin 6.25 Hz），但 UI 只显示 0～3000 Hz。

**对 FT8CN 的启示**：

- 最接近 JTDX 的做法不是“音频带通”，而是**在瀑布图上屏蔽本段之外的频点**，再调用 `FindSync`；
- 由于现有 native 库导出了 `setMagToZero(decoder_t*, int, int)` 符号（4 个 ABI 都有），可以写一个很小的 JNI shim，在 `DecoderMonitorPressFloat()` 之后、每轮 `FindSync()` 之前，把本段之外的 `mag` 清零。这样不需要音频滤波，也没有边界衰减；
- 但 `setMagToZero` 每次只清零一个 bin，且第二个参数是上界检查而不是区间终点（反汇编已确认），shim 需要在 native 循环里按 bin 逐个调用；
- 它只清零 `mag`（同步/LLR 使用），不清零 `mag2`（SNR 使用）；由于 SNR 只取候选附近的频点，通常不受影响，但需要实测确认；
- 该方案仍然不会减少 `FindSync` 的全 bin 循环，只减少候选数量，所以加速主要来自逐候选解码的并行；要减少同步开销，仍需 native 频率范围参数或降采样。

### 3.7 原版 ft8_lib 带来的最优路线（路线 D）

本机 `D:\Desktop\ft8_lib` 是 kgoba/ft8_lib 的完整源码（`origin` 指向 `https://github.com/kgoba/ft8_lib.git`，最新提交 `9fec6ca`，2025-08-24）。它不是 FT8CN 的“丐改版”，而是 FT8CN 所用解码器的上游原版。它的存在把“缺 0.93 源码”这个最大障碍变成了“可以自建解码核心”。

#### （1）原版库已经具备的关键能力

- **频率范围是真实生效的**
  `common/monitor.c:102-107`：
  ```c
  me->min_bin = (int)(cfg->f_min * symbol_period);
  me->max_bin = (int)(cfg->f_max * symbol_period) + 1;
  const int num_bins = me->max_bin - me->min_bin;
  ```
  `monitor_process()` 只把 `[min_bin, max_bin)` 内的频点写入瀑布图（`monitor.c:166-188`），
  `ftx_find_candidates()` 也只遍历 `wf->num_bins`（`ft8/decode.c:190`）。
  这与 FT8CN 0.93 中“`f_min/f_max` 写了但不用”完全不同。

- **任意采样率**
  `block_size`、`subblock_size`、`nfft`、`num_bins` 都由 `cfg->sample_rate` 推导（`monitor.c:60-105`），频率格点间距始终是 6.25 Hz。因此可以直接用 4000/3000/2400 Hz 等低采样率处理窄带切片。

- **候选数与迭代次数可控**
  `ftx_find_candidates(wf, num_candidates, heap, min_score)` 的候选数由调用者决定；
  `ftx_decode_candidate(wf, cand, max_iterations, ...)` 的 LDPC 迭代次数也由调用者决定（`ft8/decode.h:81-90`）。深解可以直接传 200，不需要 `setDecodeMode`。

- **实例状态干净**
  `monitor_t`/`ftx_waterfall_t` 都是调用者分配的结构，`decode.c` 只有只读常量表，没有可变全局状态。多个切片共享一个只读瀑布图、并行解码在结构上是安全的。

- **编码器可用于信号抵消**
  `ft8_encode(payload, tones)`（`ft8/encode.h:24`）能把 77 bit payload 还原成 79 个 tone；配合瀑布图清零即可实现类似 FT8CN `doSubtractSignal` 的深解抵消。

#### （2）最优架构：共享瀑布图 + 分段候选搜索

不需要“每片一个 decoder”，也不需要带通或 shim：

```
整段 12 kHz 音频
  ↓
一次 monitor_process()，生成完整瀑布图（0～约 5950 Hz）
  ↓
固定切片网格（例如 4 片，每片 1500 Hz，网格与线程数无关）
  ↓
线程池并行：每片在“共享只读瀑布图”上执行
    find_candidates_range(wf, K, heap, min_score, bin_lo, bin_hi)
    → 对返回的候选并行 ftx_decode_candidate(..., 200)
  ↓
按片序合并结果、去重
  ↓
串行抵消本轮已解信号（ft8_encode → 清零对应 79×8 个 tone bin）
  ↓
未超时且有新消息 → 下一轮
```

与 JTDX 的对比：

| 维度 | JTDX | 本方案（路线 D） |
| --- | --- | --- |
| 频谱数据 | 每个线程各自计算一份全带频谱 | **只算一次**，所有线程共享只读瀑布图 |
| 候选范围 | 每线程 `nfa..nfb` | 每片 `bin_lo..bin_hi`，候选中心频率 |
| 边界信号 | 频谱完整，tones 可越界 | 频谱完整，tones 可越界，**无边界损失** |
| 候选预算 | 每段 450（改造版 2000） | 每片可配置（建议 120～200） |
| 结果确定性 | 改造版与线程数无关 | 固定网格 + 按片序合并，**与线程数无关** |
| FFT 开销 | 每线程重复 | **只一次** |
| 加速上限 | 受重复 FFT 限制 | 接近核数上限 |

这是目前**理论最优、也最干净**的方案：没有音频滤波、没有边界衰减、没有重复 FFT、没有版本绑定的 shim，且能自由提高候选上限和 LDPC 迭代次数。

#### （2.1）桌面 PoC 实测（已做）

为了验证路线 D，已经在临时目录复制了一份 ft8_lib（未修改 `D:\Desktop\ft8_lib` 原仓库），用 MinGW gcc 16.2 编译，并做了三组对比：

- 用 `gen_ft8` 生成已知频率的 15 秒 WAV（1000 / 1980 / 1990 / 2000 / 2050 Hz）；
- 方案 1：每个切片单独 `monitor_init(f_min, f_max)`，即“带限瀑布图”；
- 方案 2：**一次生成完整瀑布图（0～5950 Hz），给 `ftx_find_candidates()` 增加 `bin_lo/bin_hi` 参数**，只限制候选中心频率。

实测结果：

| 信号频率 | 完整瀑布 + 分段候选 | 每片单独 monitor（无重叠） |
| --- | --- | --- |
| 1000 Hz | 正确解出 | 低片 [0,1000) 丢失，中片 [1000,2000) 正确 |
| 1980 Hz | 中片 [1000,2000) 正确解出 4 条 | 中片 0 候选；高片 1 候选但解码失败 |
| 1990 Hz | 中片 [1000,2000) 正确解出 3 条 | 中片 0 候选；高片 0 候选，**两片都丢失** |
| 2000 Hz | 高片 [2000,3000) 正确 | 高片正确（下边界包含） |
| 2050 Hz | 高片 [2000,3000) 正确 | 高片正确 |

结论：

- **每片单独 monitor 会在上边界损失约 44 Hz（7 个 bin）内的信号**，因为 `ftx_find_candidates()` 要求 `freq_offset + 7 < num_bins`，而切片外的高频 tone 没有存储；
- **共享完整瀑布图 + 分段候选搜索没有这个损失**，1990 Hz 的信号在中片被正确解出，不需要重叠频段；
- 这与 JTDX “切候选范围、不切频谱”的做法一致，也证明路线 D 的架构是可行的；
- PoC 目前只验证了单信号、25 次 LDPC 迭代、无深解抵消；多信号、200 次迭代、Android 线程/内存仍需继续测试。

#### （3）需要在 ft8_lib 上补的东西

原版库是“轻量解码器”，不是 FT8CN 的完整应用核心，移植时需要补：

1. **候选搜索范围参数**
   给 `ftx_find_candidates()` 增加 `bin_lo/bin_hi` 参数（或复制一个 `ftx_find_candidates_range()`），只改候选中心频率的循环范围。约 20 行。
2. **深解与信号抵消**
   原版没有多 pass/抵消。可用 `ft8_encode()` 生成 tone，再清零瀑布图中对应的 79×8 个 bin；逻辑与 FT8CN 的 `setMagToZero` 类似。需要处理时间偏移、频率偏移、重叠切片去重。
3. **SNR**
   原版 `decode_ft8.c` 用 `score * 0.5` 粗略估计 SNR；FT8CN 有 `mag2` 和 `ft8_guess_snr`。可以在 monitor 里增加一份 `float mag2`（约 1.4 MB/全带），或先接受近似 SNR。
4. **消息字段映射**
   `ftx_message_t.payload` 是 77 bit；`ftx_message_decode()` 输出文本和字段偏移（`message.h:145-150`）。需要把它映射到 FT8CN 的 `Ft8Message` 字段：`i3/n3`、`callsignFrom/To`、`extraInfo`、`maidenGrid`、`report`。
   - 呼号/网格/报告可以从字段偏移取；
   - `callFromHash10/12/22` 等哈希字段原版没有直接暴露，需要额外计算或先置 0；
   - 并行深解结果本来就不触发自动 QSO（`isDeep=true`），所以哈希字段缺失只影响“已通联”标记等显示功能，不影响主要流程。
5. **JNI 封装**
   新增 `libft8cn_parallel.so`（或独立 `libft8lib_jni.so`），导出：
   `init(sampleRate, numSamples, fMin, fMax)`、`press(float[])`、`findRange(binLo, binHi, maxCand)`、`decode(idx, maxIter)`、`getPayload()`、`subtract(...)`、`free()`。
   现有 `libft8cn.so` 保持不动，快速/深度模式不受影响。

#### （4）代价与风险

- **工作量**：桌面 PoC 1～2 天；JNI + Java 编排 1～2 周；消息映射/深解抵消/调参 1～2 周。总计约 3～5 周，明显高于 shim 路线。
- **消息兼容性**：原版 ft8_lib 的消息解析与 FT8CN 0.93 不完全一致，复杂呼号、哈希、特殊 CQ 的字段可能需要补齐；这是主要回归风险。
- **无 OSD**：原版只有 BP（LDPC）解码；FT8CN 0.93 的 `.so` 符号里也只有 `bp_decode`/`ldpc_decode`，没有 OSD，所以深度能力大致同级；若以后要追 JTDX，需要另移植 OSD。
- **需要重建构建链**：本机已有 NDK 28.2.13676358、CMake 3.22.1，构建不是障碍；但要为 4 个 ABI 产出 `.so` 并接入 Gradle。

#### （5）结论

- 如果只是**尽快验证“分段并行是否有效”**：路线 A0（shim）或路线 A（带通）更快。
- 如果目标是**做一版架构正确、可长期维护、速度和召回都最优的并行解码**：路线 D（原版 ft8_lib 共享瀑布 + 分段候选）是正确选择。
- 原版 ft8_lib 的存在，意味着“必须拿到 0.93 源码”不再是硬约束；真正的成本转移到“消息解析兼容”和“深解/抵消移植”。

## 4. 推荐方案

### 4.1 总体设计

新增第三种模式，暂名 **“并行深度解码”**（英文建议 `Parallel deep`），与“快速 / 深度”并列。其流程为：

```
录音 15 秒
  ↓
快速首轮（并行核心内部低迭代轮，保证自动程序能及时触发；不调用旧解码器）
  ↓
按固定切片网格切成 S 片（S 与线程数无关）
  ↓
每片创建一个 decoder，输入完整 12 kHz 音频
  ↓
屏蔽本片之外的瀑布图频点（优先，JTDX 等价）
  或 带通滤波 / 移频降采样（回退方案）
  ↓
线程池动态取片：FindSync → 本片候选 Analysis
  ↓
按片序合并本轮新消息 → 单线程回调 afterDecode(isDeep=true)
  ↓
各片抵消本片已解信号
  ↓
未超时且有新消息 → 下一轮
  ↓
清理所有 decoder
```

**为什么保留快速首轮**：

- 现有自动发射逻辑依赖 `isDeep=false` 的结果（`MainViewModel.java:318-325`）；
- 快速首轮通常几十到几百毫秒完成，不影响后续并行深解；
- 深度并行结果标记 `isWeakSignal=true`，只补充显示，不触发自动程序，行为与现有深度模式一致。

**为什么把“切片数”和“线程数”分开**：

- 切片数决定候选预算（每片独立 120 个候选）和召回率上限；
- 线程数只决定同时跑几片，影响墙钟时间，不应改变解码结果；
- 这与 CE3TSK 改造版 JTDX 的“固定网格、动态取片、按片序合并”一致，也避免“换个线程数结果就变”的问题。

### 4.2 阶段一：候选范围屏蔽（推荐先做，JTDX 等价）

**核心思路**：不切音频，只切候选。每个切片使用完整的 12 kHz 音频生成同一张瀑布图，然后把本片之外的 `mag` 清零，`FindSync` 自然只会返回本片候选。

实现方式按优先级：

1. **JNI shim 调用 `setMagToZero`（推荐先验证）**
   - 新增一个很小的 `libft8cnshim.so`，只包含一个 JNI 函数：
     `native void maskOutside(long decoder, int keepFromBin, int keepToBin, int numBins, int totalSize)`
   - 内部循环所有 `mag` 下标，若 `bin` 不在 `[keepFromBin, keepToBin)` 内，则调用现有库导出的 `setMagToZero(decoder, index, totalSize)`。
   - 优点：不需要音频滤波，无边界衰减，频率换算简单，最接近 JTDX；
   - 风险：依赖导出符号和 `mag` 布局；需要实测 `mag2` 对 SNR 的影响；
   - 构建：本机已有 NDK 28.2.13676358 和 CMake 3.22.1，可以新增 `src/main/cpp/CMakeLists.txt`，把 `app/libs/<abi>/libft8cn.so` 作为 `IMPORTED` 库链接。

2. **音频带通 + 重叠（回退方案）**
   - 若 shim 无法链接或语义不符，再退回带通：
     - 每片带宽 = 网格宽度 + 2 × 重叠（默认重叠 200 Hz，保证 50 Hz 宽的信号在至少一片中完整）；
     - 线性相位 FIR，约 129～257 抽头，统一补偿群延迟；
     - 每片 `InitDecoder(utc, 12000, 180000, true)` + `DecoderMonitorPressFloat(filteredAudio, decoder)`；
     - 片间结果去重。
   - 优点：不依赖 native 符号；缺点：有滤波开销和边界衰减。

3. **恢复 native 源码加 `f_min/f_max`（最优，长期）**
   - 在 `ft8_find_sync()` 中增加频率范围参数，只在本片 bin 内提取候选；
   - 无需 shim、无需滤波、无需重叠，性能与 JTDX 最接近；
   - 但缺 0.93 源码，暂不作为第一版。

**频率范围**：

- native `ft8_find_sync()` 实际扫描 0～约 5950 Hz（`num_bins = 960`，每 bin 6.25 Hz），而 UI 只显示 0～3000 Hz；
- 为了与现版本召回一致，切片网格建议覆盖 **0～6000 Hz**；
- 如果只想处理 UI 显示的 0～3000 Hz，可以作为可配置项，但会改变现有行为（3000～6000 Hz 的信号不再解码）。

**固定切片网格示例**（覆盖 0～6000 Hz）：

| 切片数 S | 每片宽度 | 每片候选上限 | 总候选预算 | 说明 |
| --- | --- | --- | --- | --- |
| 2 | 3000 Hz | 120 | 240 | 与 JTDX 2 线程类似 |
| 4 | 1500 Hz | 120 | 480 | 推荐默认 |
| 6 | 1000 Hz | 120 | 720 | 拥挤频段 |
| 8 | 750 Hz | 120 | 960 | 高负载，需实测 |

线程数默认 `min(4, max(2, CPU 核数 - 1))`，与切片数独立。

**半切片偏移的第二遍**：

- 如果使用带通/降采样（回退方案），建议在时间允许时再做一遍“网格偏移半个切片”的解码，覆盖正好落在切片边界的信号；
- 如果使用 shim 屏蔽 `mag`，候选中心频率连续覆盖，不需要第二遍（但 shim 的屏蔽边界要留 ≥100 Hz 的保护带，避免把候选自身的高频音调切掉）。

**优点**：最接近 JTDX，无音频滤波损失；实现量比恢复 native 源码小得多。

**缺点**：每片仍做全带宽 FFT 和全 bin 同步，固定开销 ×S；候选上限仍受 120/片限制。

### 4.3 阶段二：移频 + 降采样分割（性能版）

阶段一（shim 屏蔽或带通）验证通过后，把每片的预处理升级为“移频 + 低通 + 整数抽取”，以降低每片的 FFT/同步开销：

1. 把第 i 段中心频率 `f_ci` 搬到中频 `f_IF`：
   `x_i[n] = x[n] * cos(2π(f_ci - f_IF)n / 12000)`
2. 低通滤波（截止约 `B/2`）并抽取 `D` 倍，输出采样率 `fs_i = 12000 / D`。
3. 以 `fs_i` 和 `num_samples / D` 调用 `InitDecoder`。
4. 解码器报告的频率加上 `f_ci - f_IF`，得到绝对频率。
5. 时间偏移减去滤波器组延迟。

频段规划示例（若只处理 0～3000 Hz，重叠 100 Hz；覆盖 0～6000 Hz 时总计算量会更高）：

| 段数 N | 每段带宽 B | 抽取 D | 输出采样率 | 中频 | 输出频段占用 | 总计算量占比（不含滤波） |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 1600 Hz | 3 | 4000 Hz | 1000 Hz | 200～1800 Hz | 67% |
| 3 | 1100 Hz | 4 | 3000 Hz | 750 Hz | 200～1300 Hz | 75% |
| 4 | 850 Hz | 5 | 2400 Hz | 600 Hz | 175～1025 Hz | 80% |
| 6 | 600 Hz | 6 | 2000 Hz | 500 Hz | 200～800 Hz | 100% |

> 表中“总计算量占比”只考虑 FFT/同步随带宽缩放；实际还要加上混频和滤波开销，需实测。

**关键收益**：N=4 时总计算量约等于原来的 80%，但分摊到 4 个线程，墙钟时间理论上可降到 25%～35%；即使只有 2 个大核，也能接近 2 倍。

**关键前提**：0.93 解码器必须接受 2000～4000 Hz 的采样率。若实验失败，阶段二退化为“不抽取，只移频”，收益回到阶段一水平。

### 4.4 阶段三：native 层优化（长期，可选）

如果能拿到 0.93 的 C 源码（向 BG7YOZ 索取，或从 0.89 恢复并补齐差异），可以做：

1. `init_decoder` 增加 `f_min/f_max` 参数；
2. `ft8_find_sync` 只在指定 bin 范围内扫描；
3. 多个工作线程共享一份瀑布图（只读），各自持有候选/哈希表；
4. 抵消信号时用原子操作或分频段锁，避免重复计算。

这是最优解，但受 0.93 源码缺失限制，不作为当前主线。

### 4.5 路线 D：基于原版 ft8_lib 的新解码核心（推荐长期方案）

### 6.2 编排伪代码

> 下面是 A 轨（现有 native 库 + 多实例）的编排伪代码，用于快速验证；D 轨（原版 ft8_lib 共享瀑布图）的流程见 3.7 和 4.5。两条轨道共用 Java 侧的切片规划、结果合并和 UI。

```java
public final class ParallelDecodeEngine {
    private final ExecutorService pool;      // 固定大小，复用到整个 App 生命周期
    private final AtomicBoolean running = new AtomicBoolean(false);

    public void decode(float[] audio, long utc, ParallelConfig cfg, Callback cb) {
        if (!running.compareAndSet(false, true)) return; // 防止上一周期未结束
        try {
            long start = System.currentTimeMillis();

            // 1. 快速首轮：沿用现有单解码器，触发自动程序
            List<Ft8Message> fast = decodeFast(audio, utc);
            cb.onRound(utc, fast, false);

            // 2. 频段规划
            List<Band> bands = BandSplitter.plan(cfg);

            // 3. 预处理 + 创建每段解码器
            for (Band band : bands) {
                band.audio = BandSplitter.prepare(audio, band, cfg);
                band.decoder = InitDecoder(utc, band.sampleRate, band.audio.length, true);
                DecoderMonitorPressFloat(band.audio, band.decoder);
            }

            // 4. 深度轮次
            boolean changed = true;
            while (changed && System.currentTimeMillis() - start < cfg.timeoutMs) {
                changed = false;
                List<Future<List<Ft8Message>>> futures = new ArrayList<>();
                for (Band band : bands) {
                    futures.add(pool.submit(() -> decodeBand(band, start, cfg)));
                }
                List<Ft8Message> round = new ArrayList<>();
                for (Future<List<Ft8Message>> f : futures) {
                    round.addAll(f.get()); // 单线程汇总，避免共享状态竞争
                }
                List<Ft8Message> newMsgs = dedupe(round);
                if (!newMsgs.isEmpty()) {
                    changed = true;
                    cb.onRound(utc, newMsgs, true);
                    // 5. 各段抵消本段信号（下一轮前完成）
                    subtractInBands(bands, newMsgs);
                }
            }
        } finally {
            for (Band band : bands) DeleteDecoder(band.decoder);
            running.set(false);
        }
    }
}
```

### 6.3 频段规划

```
可用范围 = [freqLow, freqHigh]
总宽度 W = freqHigh - freqLow
每段核心宽度 w = W / N
每段实际带宽 B = w + overlap        // 两侧各 overlap/2
第 i 段范围 = [freqLow + i*w - overlap/2, freqLow + (i+1)*w + overlap/2]
```

边界处理：

- 第 0 段左边界不低于 `freqLow`；
- 最后一段右边界不超过 `freqHigh`；
- 段中心 `f_ci = (lo + hi) / 2`；
- 阶段二的中频 `f_IF` 取 `fs_i / 4`，保证 `f_IF ± B/2` 落在 `(0, fs_i/2)` 内。

### 6.4 滤波器与降采样实现要点

**阶段一（带通）**：

- 窗函数法设计线性相位 FIR：`h[n] = sinc(...) * window(n)`；
- 截止频率按段边界设置，过渡带约 100 Hz；
- 抽头数取奇数，默认 129（12 kHz 下过渡带约 90 Hz，阻带衰减约 60 dB）；
- 用循环卷积/滑动缓冲实现，避免每段重复分配大数组；
- 所有段使用相同抽头数和相同群延迟，时间偏移统一补偿 `(taps-1)/2 / 12000` 秒。

**阶段二（移频 + 抽取）**：

- 混频：`cos(2π(f_ci - f_IF)n / 12000)`，可预先计算并缓存每个段的 cos 表（长度 12000，按 n 取模），避免每周期重复计算三角函数；
- 低通：截止 `B/2 + 过渡带/2`；
- 抽取：先滤波再取每 D 个点，不能先抽取；
- 输出实信号，频段中心位于 `f_IF`；
- 绝对频率换算：`f_abs = f_decoded + (f_ci - f_IF)`；
- 绝对时间换算：`t_abs = t_decoded - (taps-1)/2/12000`（抽取不改变时间单位，解码器内部按 `symbol_period` 计算）。

**性能提示**：

- 混频 + 滤波可以合并成多相结构，只在抽取后的采样点上计算，避免 12 kHz 全速卷积；
- `float[]` 复用，避免每个周期产生大量垃圾对象；
- 段数多时，滤波总开销可能接近解码本身，需要基准测试决定是否默认开启阶段二。

### 6.5 深度轮次与信号抵消

- 每段维护自己的 `A91List`，只记录本段解出的信号；
- 每轮结束后，把本轮所有段的新消息按频率分配到对应段（考虑重叠区，可同时分配给相邻段），调用 `ReBuildSignal.subtractSignal()`；
- 抵消必须在下一轮 `DecoderFt8FindSync()` 之前完成；
- 终止条件：
  - 本轮没有任何新消息；
  - 或总耗时超过 `parallelTimeout`；
  - 或用户切换模式/停止监听。
- 每处理一个候选前检查一次超时，避免单个候选的 200 次 LDPC 迭代拖过 7 秒。

### 6.6 回调与线程安全

- `afterDecode()` 只在编排线程调用，每轮一次；
- 传给 `afterDecode()` 的 `ArrayList` 必须是新对象，不能与其他线程共享；
- `Ft8Message.isWeakSignal = true` 表示并行深解结果；
- 快速首轮保持 `isDeep=false`，确保自动程序照常工作；
- `decodeTimeSec.postValue()` 每轮更新一次总耗时；
- 停止监听时设置取消标志，工作线程在候选循环和轮次边界检查；`DeleteDecoder` 必须在 `finally` 中执行，避免内存泄漏。

### 6.7 异常与降级

| 场景 | 处理 |
| --- | --- |
| 线程池创建失败 / OOM | 降级为现有深度解码 |
| 某个频段 `InitDecoder` 失败 | 该段跳过，记录日志，其余段继续 |
| 某段解码抛异常 | 捕获并返回空列表，不影响其他段 |
| 上一周期未结束 | 跳过本周期并行深解，只做快速解码 |
| 设备核数 < 2 | 自动降为 2 段，或直接使用现有深度模式 |
| 温度过高 | 可选：读取 `PowerManager.getCurrentThermalStatus()`，高负载时降为 2 段 |

## 7. 性能预估

设单轮深解码耗时为：

```
T = T_fixed + T_candidate
```

- `T_fixed`：瀑布图 FFT + 全频段同步 + 内存分配；
- `T_candidate`：所有候选的 LDPC/OSD 解码与抵消。

阶段一（同采样率、S 片并行）的墙钟时间近似：

```
T_A(N) ≈ T_fixed + T_candidate / N + T_filter(N)
```

阶段二（降采样、每段固定开销约为 1/N）近似：

```
T_B(N) ≈ T_fixed / N + T_candidate / N + T_filter(N)
```

按 `T_fixed` 占 30%、`T_filter` 暂忽略估算：

| 段数 N | 阶段一加速比 | 阶段二加速比 |
| --- | --- | --- |
| 2 | 约 1.5 倍 | 约 1.8 倍 |
| 3 | 约 1.9 倍 | 约 2.5 倍 |
| 4 | 约 2.1 倍 | 约 3.2 倍 |
| 6 | 约 2.3 倍 | 约 4.0 倍（受核数限制） |

> 以上只是理论上限，实际受大小核调度、内存带宽、温度降频、滤波器开销影响。必须用真机基准校准。

**更重要的收益**：深度模式总预算固定 7 秒。单轮变快后，同样 7 秒内可以多跑几轮“抵消 + 重解”，弱信号被挖出来的概率更高。因此验收时不应只看“耗时”，还要看“同样 7 秒内解出的消息数量”。

## 8. 风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 0.93 预编译库多实例并发不安全 | 中 | 先做 2/4 线程压力测试；异常时加全局锁或退回单实例候选级并行 |
| 0.93 不支持非 12 kHz 采样率 | 中 | 阶段二前做 WAV 实验；失败则停留在阶段一 |
| 频段边界信号被切坏 | 中 | 100～200 Hz 重叠 + 结果去重；边界段优先保留重叠区候选 |
| 带通滤波引入群延迟/相位失真 | 低 | 线性相位 FIR；统一补偿群延迟；对比解码时间偏移 |
| 多段重复解码导致消息重复 | 低 | 沿用 `checkMessageSame()` 文本去重；必要时增加“文本 + 频率 ±10 Hz” |
| 7 秒内未完成，拖到下一周期 | 中 | 每候选检查超时；上一周期未结束则跳过；提供 4/6 秒更短上限 |
| 内存占用上升 | 低 | 每实例约 1.8 MB；N=4 约 7 MB，可接受；复用音频缓冲 |
| 功耗/发热增加 | 中 | 默认自动段数；高温度降级；帮助文本提示 |
| SNR 标定变化 | 低 | 频率格点仍为 6.25 Hz，理论上噪声底不变；实测对比 ±3 dB |
| 自动程序时序被深解拖慢 | 中 | 快速首轮先回调；深解结果不触发自动程序 |
| 无 native 源码，无法进一步优化 | 高 | 阶段三单独立项；先向原作者确认 0.93 源码是否可提供 |

## 11. 需要确认的问题

1. **选 A 轨还是 D 轨？**
   - A 轨：基于现有 `libft8cn.so` + shim 屏蔽，1 周左右能看到真机效果，但受 120 候选上限和全 FFT 重复限制；
   - D 轨：基于 `D:\Desktop\ft8_lib` 新建解码核心，3～5 周，架构最优、速度和召回上限最高；
   - 也可以先做 A 轨验证，再决定是否投入 D 轨。
2. **旧模式的保留方式**：推荐“入口分发”——只在 `decodeFt8()` 开头判断是否并行模式，旧快速/深度方法体原样保留；是否接受这种最小改动？如果要求旧代码“零改动”，则需要新增一个独立的监听器，会多复制一份定时/录音胶水代码。
3. **并行模式的快速首轮**：用新核心的低迭代轮（不碰旧解码器，推荐），还是复用旧快速路径（时序最一致，但新旧核心耦合）？
4. **第三种模式的定位**：是作为“深度解码”的增强（保持快速/深度两项，深度里加并行开关），还是并列增加第三个单选项？本文建议并列。
5. **参数暴露程度**：只暴露“切片数 + 线程数 + 时间上限”，还是把保护带、频率范围、降采样都放进高级设置？
6. **消息字段兼容要求**：并行模式使用原版 ft8_lib 时，复杂呼号/哈希字段可能和现有深度模式有细微差异；并行结果不触发自动 QSO 的前提下，是否接受“显示一致、哈希标记暂缺”？
7. **目标设备范围**：最低支持几核？是否需要兼容 32 位 ARM/x86 模拟器？这会影响默认切片数和线程池大小。
8. **时间上限**：保持 7 秒，还是允许用户调到 10 秒（可能压缩自动回复窗口）？
9. **是否接受“并行深解结果不触发自动程序”**（与现有深度模式一致）？

是否还有问题？
